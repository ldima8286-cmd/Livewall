# Архитектура

## Слои

```
main.cpp            точка входа (wWinMain / wmain для консольной сборки)
app.cpp/.h          жизненный цикл, трей, настройки, цикл кадров
desktop.cpp/.h      окна в слое обоев Explorer (WorkerW), мониторы, health-check
renderer.cpp/.h     D3D11: устройство, swap chain на окно, шейдер вывода кадра
media.h             интерфейс MediaSource + фабрика по расширению
media_wic.cpp       GIF и статичные изображения (Windows Imaging Component)
media_mf.cpp        видео (Media Foundation SourceReader), зацикливание
settings.cpp/.h     INI в %LOCALAPPDATA%\LiveWall
util.cpp/.h         пути, UTF-8/UTF-16, HRESULT
log.cpp/.h          файловый журнал с ротацией
```

Зависимости направлены вниз: `app` знает про `desktop`, `renderer` и `media`;
`renderer`/`media` ничего не знают про окна приложения и друг про друга.

## Потоки

Всё выполняется в одном UI-потоке:

```
PeekMessage/DispatchMessage → Tick → Advance(источника) → UploadFrame → Render → Present
                                    ↓                    ↓
                              медиа-декодер        1 текстура на кадр
```

Плюсы: не нужна синхронизация, ошибки воспроизведения видны сразу. Минусы:
декодирование видео делит поток с обработкой сообщений, поэтому длинные
операции (открытие файла, `SetCurrentMediaType`) могут на мгновение подвесить
трей. Вынос декодера в отдельный поток — следующий шаг (см. ROADMAP).

Медиа и D3D работают в **MTA** (`CoInitializeEx(COINIT_MULTITHREADED)`):
`IMFSourceReader` и WIC этого ожидают, а FilterGraph-подобные STA-компоненты
не используются.

## Кадры

`MediaSource::Advance(dt)` двигает внутренние часы и возвращает `true`, когда
в `CurrentFrame()` появились новые пиксели. Формат кадра всегда один:

```
BGRA8, stride = width * 4, строки сверху вниз
```

Это позволяет рендереру не знать, откуда пришёл кадр, и держать один
шейдерный путь. `Frame::serial` увеличивается источником, рендерер сравнивает
его со своим и пропускает лишние `UploadFrame`.

- **WIC**: кадр декодируется по требованию (`GetFrame(i)`), задержка читается
  из `/grctlext/Delay` (единицы — 10 мс), значения < 20 мс приводятся к 100 мс,
  как это делают браузеры. За один тик пропускается не больше 4 кадров.
- **Media Foundation**: `IMFSourceReader` с `MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING`
  отдаёт RGB32. Строка может быть с отрицательным stride (bottom-up) — это
  обрабатывается. Кадры подаются по timestamp из сэмпла, а не «как пришли»,
  поэтому 24 fps видео на 60 Гц дисплее не ускоряется. По `ENDOFSTREAM`
  выполняется `SetCurrentPosition(GUID_NULL, 0)` + `Flush`, часы сбрасываются в 0.

## Рендеринг

- Одно `ID3D11Device` на процесс, по одному `IDXGISwapChain` на окно.
- Swap effect — **`DXGI_SWAP_EFFECT_DISCARD`** (bitblt-модель). Flip-модель
  плохо работает с дочерними окнами, а окно обоев — именно дочернее окно
  чужого процесса.
- `Present(0, 0)`: вертикальную синхронизацию делает DWM, а темп задаёт
  `App` через ограничение fps. Иначе на двух мониторах каждый кадр ждал бы
  vsync дважды.
- Шейдер: полноэкранный треугольник по `SV_VertexID`, в пиксельном шейдере
  UV масштабируются под режим (`fit`/`fill`/`stretch`); при `fit` за пределами
  изображения рисуется фон, при `fill` UV зажимаются.
- Шейдеры компилируются из встроенного исходника через `D3DCompile` при
  старте — не нужен шаг `fxc` в сборке, ошибки видны в журнале.
- Потеря устройства (`DXGI_ERROR_DEVICE_REMOVED`) поднимает флаг: `App`
  пересоздаёт рендерер и заново вешает окна.

## Слой обоев

`DesktopHost::Start()`:

1. Находит `Progman`.
2. Отправляет `0x052C` (классический вариант), затем `0x052C` с `wParam=0xD,
   lParam=1`, затем ищет `WorkerW` как ребёнка `Progman`, и только в крайнем
   случае использует сам `Progman` (окно уводится в `HWND_BOTTOM`, чтобы не
   закрыть иконки).
3. `EnumDisplayMonitors` → на каждый монитор создаётся `WS_POPUP`-окно,
   прячется, `SetParent(workerw)`, стиль меняется на `WS_CHILD`, позиция
   пересчитывается через `ScreenToClient(parent)`.
4. `WM_NCHITTEST → HTTRANSPARENT`: клики по рабочему столу не перехватываются.

`CheckHealth()` вызывается раз в 2 секунды и замечает: исчезновение
`WorkerW`, закрытие/перепривязку окна, изменение числа мониторов. Любое из
событий → `Rebuild()`.

`TaskbarCreated` (перезапуск Explorer) обрабатывается отдельно: трей
пересоздаётся, а перестройка слоя откладывается на 800 мс, чтобы Explorer
успел создать `Progman`.

## Пауза

`App::IsPaused()` пересчитывается не чаще 4 раз в секунду:

- пользовательская пауза из трея;
- `WTS_SESSION_LOCK` (сеанс заблокирован);
- `SHQueryUserNotificationState` = `QUNS_BUSY` / `QUNS_RUNNING_D3D_FULL_SCREEN` /
  `QUNS_PRESENTATION_MODE` (игра или полноэкранное видео);
- опционально — работа от батареи.

В паузе не вызывается `Advance()` и не выполняется `Present()`; последний
кадр остаётся на экране.

## Один экземпляр, CLI и установка

Экземпляр один на сеанс: именованный мьютекс `Local\LiveWall.SingleInstance`.
Второй процесс разбирает командную строку и передаёт команду первому:

```
livewall.exe --open file.mp4   → WM_COPYDATA (путь) → PostMessage(WM_APP+2)
livewall.exe --pause           → PostMessage(WM_APP+2, Pause)
livewall.exe --quit            → PostMessage(WM_APP+2, Quit)
```

Приёмник сначала копирует строку пути (буфер отправителя живёт только на время
`SendMessage`), затем обрабатывает команду из очереди сообщений — поэтому
диалог выбора файла никогда не блокирует процесс-отправитель. Если экземпляра
нет, служебные команды (`--pause`, `--quit`, …) завершаются с кодом 0 и ничего
не запускают.

Настройки ищутся в `%LOCALAPPDATA%\LiveWall`, но если рядом с `livewall.exe`
лежит `settings.ini` (или пустой `livewall.ini`), используется папка программы —
это portable-режим, в нём же оказывается журнал.

Установщик (`installer/livewall.iss`, Inno Setup 6) ставит программу
per-user в `%LOCALAPPDATA%\Programs\LiveWall`, создаёт ярлыки и запись
автозапуска `HKCU\...\Run\LiveWall` с флагом `--autostart`, а при удалении
вызывает `livewall.exe --quit` и удаляет настройки.

## Почему не оверлей

Вариант «прозрачное topmost-окно над рабочим столом» отвергнут: оно
перехватывает клики, ломает перетаскивание иконок и конфликтует с
полноэкранными приложениями. Слой `WorkerW` — единственный способ рисовать
*под* иконками, который используют все существующие реализации.
